# Auditoría de Permisos y Policies: Mapeo de Páginas y Endpoints del Sistema (Administrador y Docente)

## 1. Resumen Ejecutivo y Alcance del Módulo Administrador

Este documento compila el inventario completo de las páginas y endpoints HTTP del sistema UTAMED tanto para el perfil de **Administrador / SuperAdmin** (`/admin/*`) como para el perfil de **Docente / Profesor / Jefe de Carrera** (`/docente/*`), detallando los métodos HTTP, rutas, controladores receptores, tipos de respuesta y descripción funcional.

### Arquitectura de Control de Acceso
1. **Middleware de Capa 1 (Rutas Web)**:
   - Las rutas de administración están agrupadas bajo el prefijo `/admin` con middleware `['auth', 'verified', 'is_admin']` y nombradas con el prefijo `admin.`.
   - `is_admin` (`\App\Http\Middleware\IsAdmin`) restringe el acceso al panel a usuarios que posean rol `Administrador` o `SuperAdmin` (o con `es_superadmin = true`).
2. **Capa 2 (Policies & Gates - Autorización Centralizada con `$user->can('action', $thing)`)**:
   - Políticas en [`app/Policies/`](file:///c:/Users/dyri0n/Code/utamed/app/Policies) que heredan de `app/Policies/Base/Base*Policy` mediante el trait [`HasBasePolicyMethods`](file:///c:/Users/dyri0n/Code/utamed/app/Policies/Base/Traits/HasBasePolicyMethods.php).
   - Invocación estándar mediante el método centralizado `$user->can('action', $thing)` (ej. `$user->can('viewAny', Modelo::class)`, `$user->can('update', $modelo)`).
   - Soporta bypass para SuperAdmin en `before()`, resolución de contexto jerárquico (`ContextAware`) y evaluación granular con [`PermissionValidator`](file:///c:/Users/dyri0n/Code/utamed/app/Services/Authorization/PermissionValidator.php) contra la base de datos RBAC.
   - Catálogo de permisos tipados en el enum [`App\Support\Permissions`](file:///c:/Users/dyri0n/Code/utamed/app/Support/Permissions.php).
3. **Capa 3 (Validaciones de Contexto y RBAC en Controladores)**:
   - Métodos en controladores con comprobaciones adicionales (`assertPuedeSincronizarPermisos`, restricciones por tipo de rol, protección contra escalada de privilegios y auditoría en canal `seguridad`).

## 3. Alcance y Arquitectura de Control de Acceso: Módulo Docente / Profesor

El módulo docente abarca las funciones que un profesor realiza en sus cursos asignados (como **Docente Titular**, **Docente Colegiado**, **Ayudante** o con rol de **Jefe de Carrera**).

### Arquitectura de Control de Acceso Docente
1. **Middleware Perimetral (Capa 1)**:
   - Rutas agrupadas bajo el prefijo `/docente` con middleware `['auth', 'verified', 'is_docente']` y nombradas `docente.*`.
   - `is_docente` verifica que el usuario posea perfil docente o roles contextuales docentes activos.
2. **Autorización Contextual por Entidad (Capa 2 - RelBAC & Policies)**:
   - Cada acción verifica la pertenencia o titularidad del docente sobre el recurso evaluado (`$curso`, `$componente`, `$actividad`, `$programa`) mediante Policies (`CursoPolicy`, `ComponentePolicy`, `ActividadPolicy`, `ProgramaPolicy`).
   - El estándar obligatorio es la invocación de `$user->can('action', $model)` aprovechando la resolución automática del contexto vía el trait / contrato [`HasContext`](file:///c:/Users/dyri0n/Code/utamed/app/Contracts/HasContext.php).
3. **Delegación Granular y Roles Especiales (Capa 3)**:
   - Los Docentes Titulares pueden delegar permisos granulares a ayudantes y docentes colegiados (ej. edición de syllabus o toma de asistencia) mediante [`CursoPermisosController`](file:///c:/Users/dyri0n/Code/utamed/app/Http/Controllers/Docente/CursoPermisosController.php) y [`DelegacionPermisosController`](file:///c:/Users/dyri0n/Code/utamed/app/Http/Controllers/Docente/DelegacionPermisosController.php).
   - Los Jefes de Carrera cuentan con el sub-prefijo `/docente/jefe-carrera/*` para la revisión de programas, planes, mallas y seguimiento curricular de su carrera asignada.
